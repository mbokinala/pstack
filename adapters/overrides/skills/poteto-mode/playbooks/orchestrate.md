### Orchestrate

**Own the program through clear briefs, a durable queue, and evidence for every landed unit.** Use this for project-scale work that outlives one worker. One task driven to a predicate belongs to Autonomous run; one ambitious task needing a custom method belongs to **figure-it-out**. Scale coordination to the amount of work.

Three rules carry the program:

- Completions are queue events. Finish the current critical section before draining them.
- Every worker launch and resume receives the standing orders and current scope.
- The brief is the contract. A worker cannot recover requirements it was never given.

#### Capability check

Read `references/pstack-runtime.md` before choosing the execution model. Native delegation, parallelism, nesting, remote workers, model overrides, and durable background execution are optional host capabilities. Do not assume them. If delegation is unavailable, run the scoped units sequentially and keep the same acceptance evidence. If a required independence or environment gate cannot be met, record `verifier-blocked` and continue independent work.

The bookkeeping CLI is `scripts/orch/orch.ts` relative to this skill and requires Bun and its bundled dependencies. It records state; it never spawns, waits, or schedules. Check `--help` for exact commands. The existing `frontier set` command specifically requires Graphite metadata. Do not claim that it supports a plain Git stack. Without Bun, keep the same fields in plain local files with one writer. Without Graphite, use an explicit dependency table based on observed branches and PR bases instead of running `frontier set`.

#### Roles and placement

- **Coordinator.** Frames the work, authors briefs, drains completions, owns status and judgment, and verifies integration receipts. Delegate substantial implementation while useful native agents are available. Perform scoped work directly when delegation is unavailable or an extra coordination layer would cost more than it saves.
- **Track coordinator.** Add one only when the root cannot usefully manage the ready units. It owns its track, receives all standing orders, and returns aggregates rather than raw child logs. Nested delegation is conditional on host support and concurrency limits.
- **Worker.** One writer per worktree or branch. The brief defines paths, acceptance, allowed operations, and where evidence lives. Use a remote environment only when actually available and appropriate. Tasks needing local auth, browser state, simulators, or transcript exports stay where those capabilities exist.
- **Verifier.** Reviews the current artifact and evidence independently where the host supports it. Prefer a different configured model family when available. Same-model agents provide separate contexts; sequential passes in the parent are not independent verification. Reviewers do not mutate the implementation or external services.
- **Integrator.** Exactly one owner per shared stack. Serializes rebases, retargeting, merges, and tracking-tool operations. Workers do not alter sibling history.

Avoid predetermined agent trees. Choose tracks from real dependencies and cap the rolling worker window at what the host and coordinator can handle.

#### Store layout

Use `.pstack/state/orchestrate/<project-slug>/` in the active project, or an explicitly selected local task store. Record its absolute path in briefs. Private session state stays local unless the user requests it as a repository artifact. Every file has one writer.

Invoke the CLI as `bun <absolute-skill-dir>/scripts/orch/orch.ts --store <absolute-store-dir> <command>`, abbreviated below as `orch`. Never substitute a guessed host-specific agent store.

- `preferences.md` holds numbered standing orders: scope, forbidden paths, model policy, verification bar, integration owner, and escalation limits. Include its actual content in remote briefs and all resumes; a local agent may read an explicitly accessible path.
- `overview.md` records durable artifact pointers and program decisions.
- `units.tsv` records unit ID, track, state, branch, PR, current head SHA, and brief path.
- `ledger.tsv` records verdicts for a PR number and exact head SHA, including verifier identity and evidence path.
- `frontier.json` is generated by the CLI for Graphite-managed stacks. With no Graphite, keep a separate `dependencies.tsv` containing unit, base branch/PR, head SHA, observed state, and verification key. Do not fabricate CLI-generated state.
- `inbox/` holds completion pointers. `gates.md` holds concrete unresolved user decisions. A suggested default is not approval for an external or irreversible action.
- `decisions.tsv` is the trail through **show-me-your-work**.
- `status.md` is derived from unit and ledger facts at each drain, not maintained as a second narrative source of truth.

#### The brief

Every worker receives the fields below, scaled to its scope. Collapse a one-command unit to a paragraph with the same relevant facts.

```text
GOAL         outcome a worker can execute without this conversation
SCOPE        exclusive worktree/branch and paths allowed or forbidden
CONTEXT      discovered skill paths, relevant artifacts, dependency reports
ACCEPTANCE   checkable conditions
VERIFY       exact commands or available runtime capability and known limits
TIMEBOX      effort/runtime boundary; on expiry return partial evidence
FORBIDDEN    shared history changes and operations outside this unit's authority
REPORT       status, branch, head SHA, artifacts, verdict, commands run, deviations
STANDING     current standing orders
```

A dependency requires relaying evidence, not merely waiting. Give downstream workers the upstream result and its exact artifact identity. A field essential to acceptance that cannot be filled means the unit needs more scoping. Audit a sample of briefs as the wave runs; fix the template if scope decays. Fresh consolidated briefs are preferable to a chain of contradictory resumes.

#### Program loop

1. **Frame.** State a countable completion predicate and delivery boundary. Quantify units, dependencies, effort, and any user-supplied budget. If one session can own the work simply, use Autonomous run. Define what “landed” means for this request: a local verified change, prepared PR, or authorized merge. Do not turn implementation permission into publication or merge permission. Resolve contested design through **arena** when warranted.
2. **Initialize.** Run `orch init` when available, write standing orders, and establish the decision trail. Seed Graphite frontier state only when that tool's tracked stack is available. Otherwise record observed branch/PR dependencies in the plain dependency table.
3. **Pilot.** Take one representative unit from brief through implementation and appropriate verification to the authorized delivery boundary. Use its evidence to correct the brief, environment, and unit size before broad fan-out. Cheap identical units can share one simple pilot recipe; novel or high-impact units need stronger independent review.
4. **Scale.** Fill a rolling window of ready workers within host capacity. Refill as results arrive rather than waiting for the slowest member of a batch. Relay dependency evidence and reconcile every child. When there is no agent tool, process the same ready queue sequentially and disclose the limitation.
5. **Drain.** At the end of a critical section, a track checkpoint, an available event notification, or before reporting, process the completion pointers as described below. Keep useful local work moving between notifications.
6. **Integrate.** Begin as units verify. Keep the lowest outstanding dependency sound before building higher layers. The single integration owner checks exact SHAs, authorized delivery, and current verification receipts before changing shared state.
7. **Close or checkpoint.** Reconcile every launched agent and unit, test the completion predicate against real artifacts, and confirm delivered heads have current verdicts. Review the decision trail using **show-me-your-work**, disclosing absent cross-model review. Keep durable state and exact resume instructions when the host/session ends or a real blocker remains. Do not claim a scheduled continuation unless a native scheduling tool actually registered it.

#### Queue and drain

- On completion, append a pointer through `orch inbox push <agent> <unit> <status> [--report PATH]` when using the CLI. Finish brief authoring, an integration operation, or another state update before inspecting the result in depth.
- Start a drain with `orch inbox drain`. Classify every pointer as delivered, needs verification, failed, stale, or unrelated. New arrivals can wait for the next drain.
- Record resulting state with `orch unit add`, `orch unit set`, and `orch ledger record` as appropriate. Derive `status.md` through `orch status`. Use command help for the required options; a verdict needs an evidence path.
- Verification that requires reading a substantial diff is a scoped review unit, not hidden work inside a bookkeeping drain.
- Account for each child as completed, still running with evidence, replaced, or explicitly absorbed. Late results reconcile against the current head and dependency state before acceptance.
- Report counts, changes, and open gates from the tables. Do not infer success from the number of completion messages.

#### Stack safety

One integration owner serializes mutations per stack. Capture ordered dependencies and exact head SHAs from actual Git/PR state. Recompute after merges, rebases, retargets, and new head commits. Graphite users must compute its frontier in the checkout where its tracking metadata exists; an empty view in an unrelated clone is not evidence that the stack is empty.

Workers do not rebase other units, run the integration owner's stack tooling, or close/retarget base PRs. A babysitter follows `playbooks/babysit.md` for its assigned immutable frontier snapshot and reports conflicts to the integrator. A stale snapshot cannot authorize a new merge. When shipping is authorized, apply `playbooks/shipping.md`; only the contiguous independently verified run from the root may land. A later change to a verified head invalidates its old receipt.

Post-merge checks for reverts and CI failures use currently available event or polling tools. Do not create an unrequested persistent watcher.

#### Verification

For a cheap mechanical unit, the worker runs the acceptance command and supplies its output, and the coordinator checks the receipt. Expensive, behaviorally complex, or high-impact work earns an independent verifier. Repeat tests only when new artifacts or unresolved evidence gaps justify it.

The ledger verdicts are `live-ui-verified`, `unit-test-verified`, `type-check-only`, `verifier-blocked`, and `verifier-failed`. A row is keyed by PR number plus exact head SHA. `orch ledger check <pr> <sha>` checks that artifact, not the branch's name. Local units without a PR record their commit/content identity and verification evidence in the unit report until a PR identity exists.

CI green is evidence, not a behavioral verdict. Behavioral changes need more than type checking. A blocked verifier is not a pass; a failed verifier needs a fix unit. Independent verification cannot be faked with an extra parent pass. Where a workflow's shipping gate requires independence, absent native delegation remains a gate.

Externalize evidence as each unit reaches its authorized delivery boundary. Local artifacts belong in durable paths accessible to the next session; remote publishing occurs only when authorized. A remote worker's unexported ephemeral files are not a delivered result.

#### Liveness and failure

- Probe through actual host agent status, durable artifacts, and read-only repository state. Transcript modification time is not liveness. A resume may start a new turn rather than inspect the old one; use the host's documented behavior.
- Treat missing results as explicit failure events. Record the unit, last evidence, suspected failure mode, and recovery options. Scope budget/memory failures smaller. Retry transient network failures with a bound. Change a failing tool/environment only when the replacement is available. After two failed retries, replan or record a blocker rather than spawning indefinitely.
- A late worker result must match current scope and artifact state. Salvage unique findings through a fresh scoped unit; never integrate an obsolete branch blindly.
- If upstream evidence, acceptance criteria, or infrastructure makes further workers unproductive, pause new dispatch, record the stop reason, and fix the cause within scope.
- After a host restart, discover actual surviving work through supported status APIs and artifact pointers. Do not assume any agent survived. Re-read standing orders and tables, refresh dependencies, reconcile results, and resume from consolidated briefs.
- When the host cannot run longer or a user budget expires, write a terminal checkpoint with completed work, exact artifact locations, unresolved gates, and the next command or task. Ending a session is not proof the program is complete.

#### Scope and user decisions

Handle routine reversible fixes needed by the agreed outcome within existing authorization. Park unrelated improvements in local follow-ups. Batch genuine product decisions and unapproved external/irreversible actions as concrete entries in `gates.md`, while progressing independent work. Prior explicit authorization still applies; a skill does not require repeated approval of the same action.

**Reply:** completion predicate and counts from the tables, track outcomes, current dependency frontier and SHAs, evidence verdicts, abandoned units and reasons, unresolved gates, durable store and trail paths, and the exact resume point if unfinished. Link only artifacts that exist.
